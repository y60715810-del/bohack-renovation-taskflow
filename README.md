# 共序·港乡 · 家装四方协作平台

> **当前版本：直接体验，无需登录或注册。** 完整解压 ZIP 后双击 `start.cmd`，在 `http://localhost:8774` 打开交互开场，选择住户、项目经理、设计师或施工团队即可进入同一个案例。开场可跳过，进入后可切换身份；协商、排程、照片、任务确认和验收流程继续保留。案例按浏览器隔离，刷新保留进度。
>
> Python 3.11+。不要在 ZIP 压缩包内直接运行脚本。下文账号注册与邀请步骤保留为原账号模式的技术参考，当前预览不要求这些步骤。


[BoHack 2026 评审入口、复现步骤与展台二维码](docs/booth/README.md)

住户提出装修变更，设计师补齐图纸，施工团队核对材料与工期，中介方组织分工。各方确认同一版本后，系统才发布正式排期和执行任务。退回原因、版本修订、任务交付和住户验收均保留记录。

当前版本提供铺砖变更与水电点位变更两套模板，共用确认、发布、执行和验收流程。它使用真正的账号、项目成员权限和服务器数据库，手机和电脑访问同一台服务器即可共享记录。

## 五分钟启动

需要 Python 3.11 或更新版本，已在 Windows / Python 3.12 验证。首次安装依赖需要联网。

**Windows 双击 `start.cmd`。** 出现启动提示后打开 [本机平台](http://localhost:8774)。启动窗口保持运行；关闭窗口后服务停止。

或在仓库目录执行：

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:TASKFLOW_PORT = '8774'
.venv\Scripts\python.exe server.py
```

macOS / Linux：

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
TASKFLOW_PORT=8774 .venv/bin/python server.py
```

Windows 启动脚本默认监听 `0.0.0.0:8774`。其他设备连接同一局域网，打开 `http://服务器的局域网IP:8774`。手动运行时先设置 `TASKFLOW_PORT=8774`，以避开旧服务端口。这台机器的地址可用 `ipconfig` 查看；地址会随网络变化。**四个人要访问同一地址，不要每人启动一份独立数据库。** 若不能连接，检查设备网络和服务器的入站端口配置。

邀请链接沿用当前访问地址。准备邀请手机用户时，请先用局域网地址打开平台，再生成邀请；`localhost` 链接只指向打开它的设备本身。当前仓库没有公网部署地址。

## 四个人第一次如何配合

| 身份 | 操作 | 完成的标志 |
|---|---|---|
| 中介方 / 产品总监 | 注册，创建项目，填写原方案说明和图纸版本；在「成员与邀请」生成其他三种身份的邀请码 | 三位队友出现在项目成员中 |
| 住户 | 注册为住户，使用对应邀请码加入；进入「变更协商」提交原话 | 生成带原文依据、待确认事项和候选任务的协商草案 |
| 设计师 | 补齐规格、铺法、起铺点、收边和图纸版本，填写修订原因；再上传图纸 | 图纸上传时填写的版本，与方案字段一致 |
| 施工团队 | 补齐施工做法、供应商、报价范围、编号、金额、有效期、到货日、班组日期和工期；再上传报价 | 报价文件的编号与方案字段一致，报价仍有效 |
| 中介方 / 产品总监 | 指定每项确认的具体人员；调整任务名称、交付物、执行人、一个或多个确认人、截止日和方案 | 每项任务都分派到已加入项目的账号 |
| 设计师 → 施工团队 → 住户 | 依次确认当前版本，或填写原因退回 | 三项确认都通过 |
| 中介方 / 产品总监 | 点击「发布正式任务与排期」 | 正式施工方案更新，执行任务生成 |
| 施工团队与任务确认人 | 上传现场记录，按依赖顺序提交任务；指定确认人逐一确认或退回 | 全部任务确认完成，进入最终验收 |
| 住户 | 填写人工验收意见，通过或退回整改 | 验收通过后关闭本次变更 |

每个邀请码只能使用一次，三天内有效，账号身份须与邀请码一致。平台没有预置公共密码。注册后，账号角色暂不支持修改；同一身份可以有多位成员，确认和分工绑定到具体账号。

## 已实现的规则

- **确认之前不更新正式任务。** 草案修改仅形成新协商版本；三项确认完成后，由中介方发布时统一更新排期和任务。
- **修订后重新确认。** 改图纸、报价、人员或日期都会生成新版本；旧版确认保留在历史中，但不能充当新版确认。
- **退回必须有原因。** 设计/施工/住户确认、执行任务审核和最终验收都记录操作人、时间和意见。
- **任务有前置条件。** 到货与基层复核通过后才能提交铺贴任务；铺贴通过后才能提交自检。多位确认人必须全部通过。
- **缺信息就等待。** 没有确认的规格、价格和日期留空，不用 AI 编造；缺少匹配的图纸/报价文件、报价过期或日期不合理时阻止发布。
- **多人同时编辑有保护。** 提交时检查共享版本；旧页面不能覆盖队友的新修改。页面每八秒检查更新，正在填写的表单不会被自动刷新覆盖。
- **账号权限由后端检查。** 非成员不能读取项目或附件；住户不能代替设计师确认，施工人员不能代替住户最终验收。
- **过程可查看和打印。** 「确认与退回记录」展示事件；协商页保留各版字段、责任分派、原始要求。点击「打印共享协议单」可通过浏览器保存 PDF。

## 工期计算与任务模板的范围

通用分工字段采用「任务、交付物、执行人、确认人、前置条件、截止日」。团队可用 [GB/T 37507-2025 项目管理指南](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=1A62CB6675D7C79A483323B77305F776) 查阅通用项目管理参考，并用 [JGJ/T 304-2013 发布公告及附件](https://www.mohurd.gov.cn/gongkai/zc/wjk/art/2015/art_17339_224535.html) 核对住宅装修验收依据。实际验收要求由团队按项目和适用标准确认。

铺砖模板拆为到货核对、基层复核、按图铺贴和自检交付。水电点位模板提供点位与走向字段、隐蔽工序留痕、专业检测记录和 W01–W05 标准。住户提交需求时选定模板。设计与报价作为前置协商和确认事项。任务名称、交付物、人员与日期可修改，依赖关系保持样板约束。

两套模板是产品样例，不是国家工程分工标准，也尚不能可靠拆分任意装修大工程。新的施工类型需要增加相应模板、必要资料和确认规则。

系统比较两种条件方案：

1. 直接顺延：开始日取材料到货日与班组最早开工日的较晚者；交付日按施工方填写的总日历天数计算。
2. 先做可并行工作：施工方填写具体可并行内容与可追回天数后，计算缩短后的交付日。

日期包含开始当天，按日历天计算，暂不计算节假日、班组资源冲突和逐道工序时长。可追回天数由施工方提供并由相关人员确认，不能把这个结果当作已证明的最优工期。

供应商暂作为报价来源记录，由施工团队或中介方上传资料；登录主体保持住户、中介方、设计师、施工团队四类。

## AI 与资料核对

不配置模型时，平台会明确显示「规则模板草案 · 未调用模型」，仍可完成整个协作流程。规则先识别原话中的目标铺法及规格，责任草案使用固定样板，最终均由人确认。

可选接入兼容 Chat Completions、支持 JSON 输出的模型。服务器启动前，在同一个终端设置：

```powershell
$env:TASKFLOW_MODEL_URL = '你的完整 chat/completions 接口地址'
$env:TASKFLOW_MODEL_NAME = '服务商提供的模型名称'
$env:TASKFLOW_MODEL_KEY = '你的密钥'
$env:TASKFLOW_PORT = '8774'
.venv\Scripts\python.exe server.py
```

启动服务后，在「变更协商」中选择变更单。项目经理、设计师和施工方可将住户原话转成专业表述。住户可展开各方记录，点击「用大白话解释」。转述保留原文，仅用于阅读。配置云端模型后，点击转述会将对应原文发送给该服务商。密钥只在后端通过环境变量读取。未配置云端时，可用已有的 `TASKFLOW_NOTE_URL` 与 `TASKFLOW_NOTE_MODEL` 连接本机模型。


接口地址需要包含完整路径。密钥只在服务器环境变量中使用，不进入浏览器或仓库；本项目不会自动读取 `.env`。配置模型后，提交的变更原话、核对资料的文字和对应字段会发送至你配置的服务商。

- 模型用于提取原文事实、提出澄清问题，以及辅助核对资料文字；不能审批、发布任务或判定验收通过。
- 事实必须带能在原话中找到的证据片段；模型无法调用或返回异常时，会明确提示退回规则处理。
- 「核对资料清单与文字」检查当前图纸、报价和施工记录是否齐备。当前模型补充核对仅读取 UTF-8 TXT 与文件元数据，每次最多 12 份资料、每份前 6000 字；PDF、图片和 DOCX 可上传留存，但内容需人工查看。
- 规则核对能提示 `图纸版本：D01`、`报价单编号：Q01` 这样的显式编号与当前字段不一致。模型产生的冲突提示也必须带对应文件的原文片段。
- 核对报告记录版本和时间。资料齐备或没有发现冲突，都不会改变审批或验收状态。

**验证状态：未配置真实模型密钥进行在线调用；已测试接口不可用时的明确降级，以及模型返回无原文依据事实时的过滤。**

## 数据与部署

技术栈：Flask + SQLite + Waitress，前端为 HTML/CSS/JavaScript，无需 Node 构建。SQLite 事务保存共享状态和附件，密码存储哈希，登录会话使用 HttpOnly Cookie，写操作校验 CSRF 与项目版本。

用户、项目、会话与附件保存在 `instance/taskflow.sqlite3`，该目录已被 Git 忽略。备份应在停止服务后复制整个 `instance` 目录，避免遗漏 SQLite 的附属文件。不要把测试数据、密码或模型密钥提交到仓库。

| 环境变量 | 用途 | 默认值 |
|---|---|---|
| `TASKFLOW_HOST` | 监听地址 | `0.0.0.0` |
| `TASKFLOW_PORT` | 服务端口 | `8765` |
| `TASKFLOW_DATA_DIR` | 数据目录 | 仓库内 `instance` |
| `TASKFLOW_SECURE_COOKIE` | HTTPS 部署时设为 `1` | 未设置 |
| `TASKFLOW_MODEL_URL` / `TASKFLOW_MODEL_NAME` / `TASKFLOW_MODEL_KEY` | 可选模型配置 | 未设置，使用规则模式 |

本版适用于黑客松和小团队试用。尚未提供找回密码、账户管理后台、项目成员移除、推送通知或公网部署脚本。公网部署需配置 HTTPS 和可信代理的转发设置；不要直接照搬局域网 HTTP 地址作为公网产品入口。

## 证据初审与方案推荐

### 1. 施工留痕照片

- 施工团队在「图纸、报价与现场留痕」上传照片时，需选择**对应的留痕标准**（E01–E05）并填写照片说明。标准编号写进文件 `reference` 前缀，形如 `E01 | 瓷砖到场…`。
- 新增 `GET /api/files/<id>/preview`：仅当请求者是项目成员、且文件是 PNG/JPEG 时内联返回图片；权限沿用 `project_row()`。原 `/api/files/<id>` 仍是附件下载。
- 手机端上传框支持选择照片，部分浏览器会提供相机选项。

### 2. 5 条证据标准与 AI 初审

`domain.EVIDENCE_STANDARDS` 定义 5 条预设标准：E01 材料到场照片 / E02 基层复核照片 / E03 按图铺贴过程照片 / E04 关键节点照片 / E05 完工自检照片。

`POST …/evidence-review` 现在产出：

| 字段 | 含义 |
| --- | --- |
| `summary` | `{total, compliant, missing, noncompliant}` 计数 |
| `standards` | 逐条状态、中文理由、可复核依据（文件名 / 说明 / 版本） |
| `summary_text` | 人可读初审总结 |
| `disclaimer` | 明确「不判定施工质量、不代替人工审核」 |

三态定义：

- **符合**：有对应编号的照片、属于当前方案版本、说明完整。
- **缺失**：该标准完全没有留痕文件。
- **不符合**：有文件但不是照片，或照片属于已被修订的旧版本。

统计由 `domain.evidence_assessment()` 的**规则层**确定性计算，可复核、可解释，不依赖模型。配置模型后，`analysis_service.review_evidence()` 只补充带原文依据的 `findings` / `model_notes`，**不改写三态结论**，也不能输出「通过 / 批准」。未配模型时页面显示「规则核对 · 未调用模型」，统计照样完整。

> 关键词兜底只作用于没有标准编号的历史留痕；带编号的文件一律按编号匹配，避免「起铺点」这类词把 E03 的照片误算给 E04。

### 3. 施工方案推荐

`domain.recommend_plan()` 基于已有的两种条件方案（直接顺延 / 先做可并行工作）给出推荐、理由、前提与风险，随项目视图一并返回，显示在「工期方案与报价」顶部。**推荐不自动执行**：最终选择仍在中介方的「责任分派」里，且需三方确认后才能发布。可追回天数由施工方提供，推荐里会明确标注「不能当作已证明的最优工期」。

## 2026-11-14 交接版

### 工期与排程

「项目总览」按身份显示工作台：住户看交付和费用，项目经理看异常与确认进度，设计师看当前图纸和变更，施工人员看下一项任务和前置阻塞。施工首页可跳到拍照提交，也能把简短的现场问题记入项目，项目经理可在首页看到。报价、图纸和操作权限沿用项目成员与角色规则；项目尚未设置毛利字段或经营数据分级访问规则。

厨房墙砖 P0 路演用 `start-demo.cmd` 启动，进入「工期与排程」。A 点「误删图纸核验」，保留草稿并尝试发布，后端拒绝，原计划保留。B 点「采用候选排程」，查看必要工序顺延、独立保护工序可提前、材料报价差额与未核实的待工费，然后提交。C 切换设计、施工和住户，从各自项目总览的待办进入并确认，由中介发布。刷新保留进度；用新浏览器会话可以从头开始。厨房报价、D03 附件和建议是合成演示资料。

中介进入「工期与排程」后，可调整执行节点的开始日、天数、班组与前置关系。用保留开关提出删减，系统会保留该节点的原始记录。已提交的任务锁定原排程。项目模板规定的必需节点与前置关系受到保护。

在全屋通铺演示里，点击「填入调序冲突示例」，查看基层复核当天安排铺贴造成的冲突。点击「采用候选排程」后填写调整原因，切换设计师、施工团队与住户并逐一确认，再由中介发布。候选计划按日历天考虑明确录入的前置任务、材料日期与同名班组占用。旧项目的节点最初按任务截止日暂列一天，需补录实际安排。费用根据填入的费率估算，不代表合同费用。候选是可行排程，未验证全局最优。

在「执行待办」中，施工账号可对开放的任务直接上传原图。照片下方逐项展示 T 时间、A 拍摄角度、C 画面内容以及判定依据。详见 [施工照片初审口径](PHOTO_STANDARDS.md)。

视觉模型通过支持图片输入的 Chat Completions 接口接入。启动服务前设置 `TASKFLOW_VISION_URL`（完整接口地址）、`TASKFLOW_VISION_MODEL`（模型名），接口需要密钥时再设置 `TASKFLOW_VISION_KEY`。未配置时仍可比较拍摄时间，角度和内容显示待复核。照片会以去除 EXIF 的缩放副本送到配置的视觉服务。

中介账号登录后，在「创建或加入项目」页面点击「直接体验示例」，即可用当前账号打开独立的全屋通铺演示项目。进入「执行待办」后可人工确认或退回「核对瓷砖到场规格与数量」。同一账号再次打开会沿用上次的演示进度。

- **审批与留痕。** 每个新上传的施工附件需要本工序的有效标准编号和说明，附件追加保存。初审只产生报告与日志，人工确认仍控制发布、任务通过和最终验收。图片统计核对的是文件类型、编号和所属版本。
- **争议复核。** 当确认条件齐备时，协商页显示 24 小时确认期限及站内超时提醒。退回或超时后，项目参与方可以发起争议。中介方可通过项目邀请码邀请外部复核人查看项目并提交意见。发起人可在意见提交前撤回。复核意见入档后由相关人员修订，原确认人重新确认，住户保留最终验收权。提醒通过项目页面展示。
- **演示。** 双击 `start-demo.cmd`，打开 [本机演示](http://127.0.0.1:8775)。直接以中介身份打开案例和「工期与排程」。在左侧「切换身份」选择住户、设计师或施工团队，四个角色共用本浏览器的案例和进度。普通项目用 start.cmd 进入账号登录。快捷身份仅在本机演示启动模式启用。
- **验证。** 24 项自动测试通过。独立空库浏览器联调验证了四方注册、外部复核邀请、退回修订、重签发布、水电留痕和住户验收。
